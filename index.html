1Cel laboratorium

Celem laboratorium było zbudowanie kompletnego środowiska CI/CD na Debian GNU/Linux 13, łączącego GitLab CE, Jenkins i Nginx. Minimalne wymagania obejmowały dodatkowy dysk 20 GB jako SWAP, dostęp do Jenkins i GitLab przez nazwy DNS, repozytorium z przykładową stroną HTML, pobieranie aktualnego kodu przez Jenkins, deployment do /var/www oraz publikację strony przez Nginx.

Środowisko zostało rozszerzone o HTTPS z własnym CA, automatyczny webhook GitLab → Jenkins, konto developerskie, Project Access Token, Protected Branch, Merge Request workflow oraz końcowy audyt usług i portów.

WYNIK KOŃCOWY: 6/6 wymagań podstawowych + BONUS CI/CD

4Dodatkowy dysk 20 GB → SWAP

Dodatkowy dysk /dev/vdb o pojemności 20 GB przeznaczono w całości na SWAP. System posiadał już około 3.3 GB SWAP na /dev/vda4.

sudo fdisk /dev/vdb
# GPT
# jedna partycja /dev/vdb1
# typ: Linux swap

sudo mkswap /dev/vdb1
sudo swapon /dev/vdb1
sudo /usr/sbin/swapon --show
free -h

UUID nowej przestrzeni SWAP:

b4afb5a9-f624-4cba-a313-967fbfd5c6bc
sudo cp /etc/fstab /etc/fstab.bak
sudo vim /etc/fstab
# Additional 20GB swap disk /dev/vdb1
UUID=b4afb5a9-f624-4cba-a313-967fbfd5c6bc none swap sw 0 0
sudo swapoff /dev/vdb1

Po restarcie /dev/vdb1 pozostawał aktywny, a łączny SWAP wynosił około 23 GiB.

6GitLab CE

6.1. Instalacja bez automatycznej pierwszej konfiguracji

GitLab CE zainstalowano świadomie bez automatycznego uruchamiania pierwszego reconfigure:

sudo GITLAB_SKIP_RECONFIGURE=true apt install -y gitlab-ce

Była to celowa decyzja administracyjna: najpierw należało ustawić port Puma, wyłączyć wbudowany Nginx i przygotować integrację z zewnętrznym reverse proxy, a dopiero potem wykonać pierwsze właściwe gitlab-ctl reconfigure.

6.2. Konfiguracja

sudo vim /etc/gitlab/gitlab.rb
external_url 'https://gitlab.domain'
gitlab_rails['trusted_proxies'] = ['127.0.0.1']
web_server['external_users'] = ['www-data']
nginx['enable'] = false
puma['port'] = 8081

Port 8081 wybrano z powodu konfliktu z Jenkins używającym 8080. Wbudowany Nginx GitLab został wyłączony, ponieważ terminację TLS realizuje systemowy Nginx.

sudo gitlab-ctl reconfigure
sudo gitlab-ctl status
sudo ss -lntp | grep ':8081'

GitLab Puma działa na 127.0.0.1:8081, a Nginx komunikuje się z GitLab poprzez GitLab Workhorse i jego Unix socket:

/var/opt/gitlab/gitlab-workhorse/sockets/socket

6.3. Konta

W razie problemu z pierwszym logowaniem hasło root zresetowano lokalnie:

sudo gitlab-rake "gitlab:password:reset[root]"

Utworzono także zwykłego użytkownika ma, któremu nadano rolę Developer w prywatnym projekcie root/web-demo.

PASS — GitLab CE 19.4.1-ce.0 działa z zewnętrznym Nginx i lokalnym backendem Puma.

7.1. Nginx

7.2. Własne CA

Utworzono lokalny urząd certyfikacji CI-CD Lab Root CA. Klucz prywatny CA pozostał na serwerze; na klientów kopiowany był wyłącznie publiczny certyfikat CA.

/etc/nginx/ssl/lab-ca.key
/etc/nginx/ssl/lab-ca.crt

Wystawiono osobne certyfikaty z SAN dla jenkins.domain i gitlab.domain.

7.3. Reverse proxy Jenkins

server {
    listen 80;
    server_name jenkins.domain;
    return 301 https://jenkins.domain$request_uri;
}

server {
    listen 443 ssl;
    server_name jenkins.domain;

    ssl_certificate     /etc/nginx/ssl/jenkins.domain.crt;
    ssl_certificate_key /etc/nginx/ssl/jenkins.domain.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

7.4. Reverse proxy GitLab

server {
    listen 80;
    server_name gitlab.domain;
    return 301 https://gitlab.domain$request_uri;
}

server {
    listen 443 ssl;
    server_name gitlab.domain;

    ssl_certificate     /etc/nginx/ssl/gitlab.domain.crt;
    ssl_certificate_key /etc/nginx/ssl/gitlab.domain.key;

    client_max_body_size 0;

    location / {
        proxy_pass http://unix:/var/opt/gitlab/gitlab-workhorse/sockets/socket;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 3600;
        proxy_connect_timeout 300;
        proxy_redirect off;
    }
}

7.5. Klient macOS

W lokalnym /etc/hosts skonfigurowano:

192.168.64.21 jenkins.domain gitlab.domain domain

Publiczny certyfikat lab-ca.crt dodano do zaufanych certyfikatów systemowych macOS.

curl -I https://jenkins.domain
curl -I https://gitlab.domain

Jenkins zwrócił oczekiwane 403 Forbidden dla anonimowego użytkownika wraz z X-Jenkins: 2.580.1. GitLab zwrócił 302 Found do /users/sign_in. Oba testy wykonano bez -k.

Na końcu wyłączono domyślny vhost Debiana przez usunięcie wyłącznie symlinku /etc/nginx/sites-enabled/default, pozostawiając plik źródłowy.

PASS — Nginx terminuję TLS dla Jenkins i GitLab; certyfikaty są zaufane przez klienta.

8Repozytorium Git i deployment przez Jenkins

8.1. Repozytorium

W GitLab utworzono prywatny projekt root/web-demo. Na Macu przygotowano lokalne repozytorium ~/web-demo na gałęzi main.

git remote -v
# origin https://gitlab.domain/root/web-demo.git

git add index.html
git commit -m "Initial web page"
git push -u origin main

Pierwszy commit: bf09722. Kolejne wersje: 1a034e6 (1.1), f976a18 (1.2), 33d3361 (1.3), a finalny merge: dd12aee.

8.2. Katalog deploymentu

sudo groupadd webdeploy
sudo usermod -aG webdeploy jenkins
sudo usermod -aG webdeploy www-data
sudo mkdir -p /var/www/web-demo
sudo chown root:webdeploy /var/www/web-demo
sudo chmod 2775 /var/www/web-demo
sudo systemctl restart jenkins

Restart Jenkins był potrzebny, aby proces otrzymał nowe członkostwo w grupie.

8.3. Publikacja WWW

server {
    listen 80;
    server_name domain;

    root /var/www/web-demo;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

8.4. Dostęp Jenkins → GitLab

Na serwerze zainstalowany Git miał wersję 2.47.3 i ścieżkę /usr/bin/git. Własne CA dodano również do systemowego trust store Debiana:

/usr/local/share/ca-certificates/cicd-lab-ca.crt
sudo update-ca-certificates

W GitLab utworzono Project Access Token jenkins-read-repository z rolą Reporter i zakresem read_repository. W Jenkins zapisano go jako credential o ID gitlab-web-demo-read.

8.5. Job Jenkins

Freestyle job: web-demo-deploy, SCM: https://gitlab.domain/root/web-demo.git, branch: */main.

#!/bin/bash
set -e

echo "Deploying web-demo..."
install -m 0664 index.html /var/www/web-demo/index.html
echo "Deployment completed."

Build #4 wdrożył 1.0, a Build #5 ręcznie wdrożył 1.1. Plik finalnie ma właściciela jenkins:webdeploy i tryb 0664.

PASS — Jenkins pobiera kod z prywatnego GitLab i wdraża go do /var/www/web-demo.

Po zmianie strony do wersji 1.3 powstał commit:

11.4. Alertmanager 9094 — analiza i nieudana próba ograniczenia

Audyt wykazał *:9094 na IPv4. Proces Alertmanager uruchamiał się bez jawnego argumentu cluster listener, a jego domyślna wartość to 0.0.0.0:9094.

Przed eksperymentem wykonano kopię /etc/gitlab/gitlab.rb.bak-before-alertmanager, a następnie przetestowano:

# Disable Alertmanager HA cluster listener - single-node CI/CD lab
alertmanager['flags'] = {
  'cluster.listen-address' => ''
}

Po gitlab-ctl reconfigure i restarcie Alertmanager port 9094 nadal był aktywny. Wygenerowany skrypt GitLab nie zawierał oczekiwanej flagi. Nie modyfikowano ręcznie plików zarządzanych przez GitLab. Nieskuteczny blok usunięto z gitlab.rb.

Decyzja: pozostawić rzeczywisty stan *:9094 udokumentowany. Ewentualne dalsze ograniczenie wykonać na warstwie firewalla zamiast hackować pliki generowane przez GitLab.

11.5. Model bezpieczeństwa

  • Jenkins i GitLab Puma nasłuchują tylko na localhost.
  • HTTPS kończy się na Nginx.
  • Własne CA jest zaufane; nie wyłączono docelowo weryfikacji TLS.
  • Jenkins ma minimalny dostęp do repozytorium: Reporter + read_repository.
  • Webhook ma osobny Secret Token.
  • main jest Protected Branch.
  • Developer pracuje przez feature branch i Merge Request.
PASS — stan portów i zabezpieczeń został zweryfikowany, a wyjątek 9094 świadomie udokumentowany.

13.2. Najważniejsze problemy rozwiązane podczas laboratorium

  • DNS po zmianie DHCP na statyczne IPv4.
  • Konflikt portu 8080 między Jenkins i GitLab Puma.
  • Świadoma instalacja GitLab z GITLAB_SKIP_RECONFIGURE=true przed pierwszym właściwym reconfigure.
  • Uprawnienia Jenkins do katalogu deploymentu i konieczność restartu procesu po dodaniu grupy webdeploy.
  • GitLab → Jenkins: blokada outbound request do lokalnego/prywatnego adresu; zamiast globalnego zezwolenia dopuszczono jenkins.domain:443.
  • GitLab → Jenkins: niezależny problem z zaufaniem TLS rozwiązany przez /etc/gitlab/trusted-certs/cicd-lab-ca.crt.
